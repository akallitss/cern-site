VMM DAQ code map: from the browser to the chip

Which program does what in the P2 VMM DAQ, who owns it, and how a threshold travels from a text file to a VMM channel

Software 2026-11-12 vmm,daq,p2,slow-control,how-to

When you press Configure chip or Start Run in the DAQ web page, four different pieces of software written by different people run one after the other before anything reaches a VMM chip. This page says which piece does what, where it lives on the DAQ machine, who owns it, and which files you are meant to edit. It ends with the path a threshold takes from a text file to a channel, and what is and is not possible today for thresholds per channel.

State of the DAQ machine on 12 November 2026. All paths are on the DAQ machine. Words in italics at first use are in the glossary.

The short version.
  • Five layers: web page and run control → bench scripts → slow-control program → firmware → chips. Each layer only calls the one below it.
  • As a physicist you edit one kind of file: the exception files in config_ext/. Everything else is either generated or owned by a developer.
  • A chip is always written in full. There is no "change one channel" command.
  • What is in the chips cannot be read back. The record is the exception file, which is copied into every run folder.
  • A threshold per channel can already be set through the existing files (never tried yet). It cannot yet be measured.

2. The hardware, as the software names it

  • One FEC board, called fec[00], inside subsystem[00].
  • Ten hybrids, hybrid[00] to hybrid[09]. Hybrid 0 is the trigger hybrid (it receives the scintillator signal). Hybrids 1 to 9 read the detectors.
  • Two VMM3a chips per hybrid, vmm[00] and vmm[01]. In the analysis a chip has one number: chip = 2 × hybrid + vmm, so 0 to 19. Example: chip 7 is hybrid 3, vmm 1.
  • 64 channels per chip, channel[00] to channel[63].
  • Each hybrid has a small ADC that can measure one analog voltage chosen inside the chip (the monitor output): the temperature, the threshold voltage, or one channel. This is the only way to measure anything analog in a chip without taking data.

3. Layer 5: the web page and run control

This is the program you see in the browser. It decides when data is taken, writes the data files, shows plots and raises alarms. It does not know how to talk to a chip. For that it starts programs of layers 4 and 3 and looks at their exit code.

What you doFile that handles itWhat it starts

Press Warm Resetflask_app/chip_config.pythe warm-reset script alone
Press Start Rundaq_control.py, vmm_daq_control.py for every sub-run: p2basket-sc --acq-on, the capture program dumpcap, then p2basket-sc --acq-off. It also copies the exception file in use into the run folder.

Switch the low voltageflask_app/power_control.pythe TDK supply scripts of layer 4

Four rules are built into this layer. Any new tool that touches the chips has to keep them.

  1. Never write to the chips while data is being captured.
  2. A warm reset comes immediately before the configuration, never after it. A warm reset after the configuration silently erases the settings of the trigger hybrid.
  3. One chip operation at a time, and nobody else may be using the slow control at that moment (the session lock).
  4. The exception file used for a run is copied into that run's folder.

4. Layer 4: bench scripts and configuration files

Folder: /local/p2/p2testbench/TestBenchCERN. Every slow-control command is started from inside this folder.

FileWhat it is
config_base/p2b-config-cern-base.yaml The base file: every register of every chip with its default value, about 30 000 lines. There must be exactly one .yaml file in this folder. You normally never edit it.
config_ext/*.txt The exception files: short text files listing only what differs from the base (gain, peaking time, thresholds, masked channels). Every file in this folder appears in the drop-down list of the web page. This is the file you edit or generate.
p2basket_sc_config.py The configuration script. Loads the base file, applies the exception file on top, writes everything to the hardware.
p2basket_sc_warm_reset.py Resets the links to the hybrids and checks them. Its exit code is the number of hybrids that are not ready; 0 means all good.
switchOn_tdk.sh, switchOff_tdk.sh, pilot_tdkl.py Low-voltage supplies.
everything else (daq_control.sh, loop_daq.sh, config_scan/, …) The older bench DAQ and colleagues' own tests. Not used by the web page.

The same thing by hand

This is what Configure chip runs. You can type it in a terminal on the DAQ machine when no run is going on.

cd /local/p2/p2testbench/TestBenchCERN

../TestBenchCosmics/p2basket_sc_warm_reset.py -c . -b config_base/p2b-config-cern-base.yaml -W -w 3

./p2basket_sc_config.py -c . -b config_base/p2b-config-cern-base.yaml \
    -e config_ext/p2b-config-cern-ext_gain4.5_peaktime200_opt.txt
  • -c . the folder the two file names below are relative to (here: the current folder).
  • -b the base file.
  • -e the exception file.
  • -W do a warm reset now. -w 3 try up to 3 more times if a hybrid is not ready.
  • Add -v to the second command to see every exception line as it is applied.

How to read and write an exception file

One setting per line. The words are separated by spaces and their order is fixed:

Sys 0 Bec 0 Hyb 3 Vmm 1 Reg bank1spi2 Field sg 3     # gain 4.5 mV/fC
WordsMeaning
Sys 0 Bec 0subsystem 0, FEC board 0. Always these values on our stand.
Hyb 3 Vmm 1hybrid 3, its second chip (so chip 7).
Reg bank1spi2the name of the register inside the chip.
Field sgthe name of the setting inside that register (here the gain).
3the value, a whole number.
# …anything after the value is ignored: a comment.
  • A line that does not start with Sys is ignored. Start a line with # to switch it off.
  • There is no "all channels" shortcut. Setting something on 64 channels takes 64 lines.
  • If the same setting appears twice, the last line wins.
  • The comments in the existing files were typed by hand and some are wrong. Trust the values, not the comments.

The settings you will meet

RegisterFieldMeaningValues
bank1spi2sggain0…7 → 0.5, 1, 3, 4.5, 6, 9, 12, 16 mV/fC
bank1spi2stpeaking time0…3 → 200, 100, 50, 25 ns
bank1spi2sppolarity of the input charge0 negative, 1 positive
bank1spi2sngneighbour logic (a channel is also read when its neighbour fires)0 off, 1 on
bank1spi1 and bank1spi2sdtthreshold of the whole chip, in two parts (see below)0…1023 in total
channel[NN]smmask one channel1 = channel switched off
channel[NN]sdthreshold trim of one channel0…31
channel[NN]stconnect this channel to the internal test pulser0 off, 1 on
Two different settings are both called st. In register bank1spi2 it is the peaking time of the chip. In a channel[NN] register it switches the test pulser onto that channel.

5. Layer 3: the slow-control program

Slow control means everything that sets up or checks the electronics, as opposed to the fast data stream. Here it is one software package, p2basket-sc, installed in /local/p2/deploy. It comes in three forms that do the same things:

  • /local/p2/deploy/bin/p2basket-sc, a command-line tool. This is what the run control calls to start and stop the data flow.
  • a Python module called p2basket. This is what the bench scripts of layer 4 use. It only works when Python is started through /local/p2/deploy/bin/p2basket-python.
  • p2basket-gui, a window program of the same developer, and vmmdcs-p2b, the older program from the RD51 collaboration, which also contains calibration procedures.

To see which version is installed and what it can do (both commands are harmless, they send nothing):

/local/p2/deploy/bin/p2basket-sc --version
/local/p2/deploy/bin/p2basket-sc --help

What it can do

CommandEffectChanges the chips?

--read-link-status, --read-fw-version, --read-chip-id, --read-temperaturereads status informationno

Four properties that explain most surprises

  1. A chip is always written in full. --config-vmm-regs sends all 70 registers of every chip in one go. Changing the trim of one channel therefore costs a complete configuration, with the same rules as in section 3.
  2. Nothing can be read back from a chip. The VMM registers are write-only. The only record of what a chip contains is "base file + the exception file applied last".
  3. The program forgets everything when it ends. Settings exist in memory only while a command runs. That is why every command is given the base file again.
  4. One user at a time. The program takes a session lock. If a colleague is working with the slow control, a run start fails with "Session locked by …". The lock needs a folder, /run/p2basket, that disappears when the machine is rebooted.
After a reboot of the DAQ machine the folder /run/p2basket is missing and slow-control commands fail with No P2basket Runtime Service directory. Someone with administrator rights has to run
sudo systemctl start p2basket.service
once. This was the state on 12 November 2026 after the system update.

6. How a threshold reaches a channel

A VMM3a has one threshold voltage per chip, set by a 10-bit number called sdt (0 to 1023). Each of the 64 channels can then shift its own threshold a little with a 5-bit number called sd (0 to 31), the trim. So a channel does not have an independent threshold: it has the chip threshold plus a small personal correction.

The chip threshold: two lines

The 10-bit number does not fit in one register, so it is split in two:

sdt = 64 × (value in bank1spi2) + (value in bank1spi1)

Sys 0 Bec 0 Hyb 1 Vmm 0 Reg bank1spi1 Field sdt 46
Sys 0 Bec 0 Hyb 1 Vmm 0 Reg bank1spi2 Field sdt  3      # 64 × 3 + 46 = 238

To go the other way for a wanted value, for example 300: bank1spi2 gets 300 ÷ 64 rounded down = 4, bank1spi1 gets the remainder = 44.

The path

  1. You choose an exception file in the web page and press Configure chip.
  2. Layer 5 runs the warm-reset script and checks that all hybrids are ready.
  3. Layer 5 runs the configuration script with the base file and your exception file.
  4. The script loads the base file, then changes one value in memory for each line of the exception file.
  5. The script calls config-vmm-regs: layer 3 sends one packet per chip, 20 in total.
  6. The firmware shifts each packet into its chip.
  7. At Start Run the exception file is copied into the run folder.

7. Thresholds per channel: what exists today

QuestionAnswer on 12 November 2026
Can the hardware and firmware take a trim per channel? Yes. The trim is part of the channel register that is already written at every configuration, and the older RD51 program wrote trims to this same electronics in November 2025.
Can we set one with our files? The way exists: a line with Field sd, handled by the same code as the mask lines we use every day. It has never been tried: all 1280 trims are 0 in the base file and no exception file sets one.
Can we read back what was set? Not from the chip. Only from the exception file kept with the run.
Can we measure the real threshold of a channel? Not yet. The slow-control library contains code for it (through the monitor output and the hybrid ADC), but no command gives access to it. Only the temperature measurement is available.
Is there another way to see a channel's threshold? From data: the lowest amplitude a channel records and its noise rate both move with the threshold. Slower, but it works today.

A trim line would look like this (hybrid 3, second chip, channel 45, trim 12):

Sys 0 Bec 0 Hyb 3 Vmm 1 Reg channel[45] Field sd 12

Channel numbers below 10 are written with two digits: channel[07].

Do not use trim lines for real data yet. How much one trim step moves the threshold on our chips, and in which direction, has not been measured. The first test is planned on a single chip with half of its channels left untouched as a reference.

Planned next steps

  1. A small tool that turns a table of trims (chip, channel, value) into an exception file, and a second one that prints what any exception file sets, chip by chip.
  2. A test on one chip: the same settings with trim 0, 15 and 31, compared in the data.
  3. Access to the threshold measurement, to be discussed with the slow-control developer.
  4. Equalising all channels of each chip, and comparing the spread of noise rates before and after.
  5. A panel in the web page, once the steps above work from the terminal.

Glossary

Base file
The YAML file with every register of every chip and its default value.
Channel
One of the 64 amplifier inputs of a VMM chip; one detector pad or strip.
Exception file
A text file in config_ext/ listing the settings that differ from the base file. Also called "ext file".
Exit code
A number every program returns when it ends. 0 means success. The run control uses it to know whether a script worked.
FEC
Front-End Concentrator: the board between the computer and the hybrids. Ours is an ALINX board.
Firmware
The program loaded into the programmable chips (FPGA) of the FEC and of each hybrid.
Hybrid
The small board plugged on the detector, carrying two VMM chips.
Mask
Switching a channel off so that it produces no hits (sm 1).
Monitor output
One analog pin of the VMM onto which a chosen internal voltage can be routed, to be measured by the ADC on the hybrid.
Register, field
A register is one 32-bit word of settings inside a chip. A field is one named setting inside that word.
Session lock
A file that marks the slow control as "in use by this person", so two people do not configure the chips at once.
Slow control
Setting up and checking the electronics (registers, links, temperatures), as opposed to reading the data.
Threshold (sdt)
The signal height above which a channel records a hit. One value per chip, 0 to 1023.
Trim (sd)
A small correction to the threshold of one channel, 0 to 31.
Warm reset
A reset of the FEC and of its links to the hybrids without switching the power off.
YAML
A plain-text file format for structured settings.
